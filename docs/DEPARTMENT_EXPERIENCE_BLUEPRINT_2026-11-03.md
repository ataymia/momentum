# Momentum cross-application UX reference matrix
Updated 2026-11-03. Prototype branch only. This is the design source of truth for the multi-page redesign.

## Product decision

**Not one inventory and fulfillment platform skin:** Every Momentum department should follow the task flow, information density, navigation hierarchy, list/detail behavior and action placement of its corresponding commercial software product, using Momentum branding, data models and permissions. Do not use proprietary code, branding, screenshots or identical copied assets. A consistent Momentum chrome (sidebar, global search, breadcrumbs, notifications, direct links) can wrap distinct **department-specific** interaction patterns.

No production changes, merge, deployment, external financial transaction or automated customer/employee messages without explicit approval. Existing engines, ledgers and records are preserved. Changing the page is not authorization to change its business rules.

## Non-negotiable navigation and data patterns
1. One sidebar navigation source of truth. **Every feature that previously existed as a header tab gets its own left-sidebar entry and stable URL**; do not reproduce module-level tab navigation as a second sidebar. Record-specific subviews may use contextual tabs only when appropriate to the matching commercial software app, with their own URL path.
2. Browser history, URL reload, direct deep links and keyboard accessibility work. Exactly **one** active nav item, with most specific matching URL, even when sibling routes share prefixes (e.g. /calendar and /calendar/meetings).
3. Every collection list uses the same reliable functional table foundation: each supported column can toggle asc/desc; A-Z/Z-A text, date ascending/descending, date range filters, status filter, rep filter, search, pagination. Every row has linked detail. Persist filters in URL where appropriate. Type-safe sort values; blanks sorted consistently.
4. Department-specific lists and forms are **not interchangeable**: HR employee cards/timeoff, Payroll pay runs, Commerce sales orders, Inventory stock custody, Marketing campaigns and Finance accounts each have relevant fields, actions and workflows.
5. Record relationship IDs and their original history remain canonical across redesign. Parent/child account consolidation is a reviewed workflow preserving all links and historical earnings.
6. Authorization is enforced by backend role/record scope, not by removing sidebar entries alone.
7. Statuses and numbers distinguish proposed, projected, unverified, calculated, earned, invoiced, collected and settled. Prototype placeholder views are labeled; old pages remain reachable until equivalent workflow proven.
8. Mobile driver, employee, and customer interfaces must be explicitly tested separately from executive desktop navigation.

## Prototype acceptance checklist
- [ ] HR opens People-equivalent employee profile and request experience, no payroll-company private data for basic employees.
- [ ] Payroll opens payroll-equivalent pay run list + status-aware record path, not generic inventory tiles.
- [ ] CRM lists sort by all displayed columns and each has direct record links; route management is separate from account map.
- [ ] Commerce orders, invoices and payments each have independent list, filter, detail, action and status experience, with preserved business controls.
- [ ] Item/product record shows actual sales-order relations and source-linked stock only.
- [ ] Marketing campaigns have their own dates, objectives, resources, ROI evidence and approval states.
- [ ] Every old header tab is represented in sidebar/left-nav and deep link.
- [ ] Driver and customer roles have their own coherent workflows and scoped data.
- [ ] All pages pass browser Back/Forward, refresh, direct URL and role access checks.
- [ ] Payment and email integration release gates unchanged.
